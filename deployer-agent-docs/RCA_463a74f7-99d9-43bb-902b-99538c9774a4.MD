# RCA — Redeploy failed at build_image (frontend yarn build/install), run 463a74f7

## What I was asked to do
Redeploy the `email-audit-panel` deployment (adityaretail.com) to ship the pending Pine Labs source fix. I fired the pipeline (resume_pipeline, force_repull=true). It failed.

## Outcome of the redeploy
Terminal failure at step **build_image**. The previously-live version is untouched and still serving (the prior active image was never replaced), so the site is NOT down — but the new code did NOT ship.

## Where it failed (evidence)
CodeBuild run `463a74f7-99d9-43bb-902b-99538c9774a4`, build `prod-deployer-app-builder:bb54c985…`:
- Backend build stage (`#29`) completed its pip install fine.
- **Frontend build stage failed**: `#26 [frontend-build 7/8] RUN ... retry_with_backoff yarn install --prefer-offline --check-files --network-timeout 100000 && yarn build`. Last captured line: `#26 29.46 [4/4] Building fresh packages...`, then the whole `docker buildx build` died: `Phase complete: BUILD State: FAILED ... COMMAND_EXECUTION_ERROR ... Reason: exit status 1`.
- The literal yarn error line is NOT retrievable from the build logs: backend and frontend stages build in parallel and the backend's pip "Downloading/Installing" output consumed CodeBuild's log read budget (first 500 lines), so the frontend stage's actual error output fell outside the readable window. Greps for `heap`/`Killed`/`error` returned nothing from the frontend stage for this reason — absence here is a log-window limitation, not proof the error is absent.

## Reproduction attempt (eph sandbox, run 463a74f7 source)
Spawned sandboxes and ran the exact build command. The frontend `yarn install` **OOM-killed the 2 GiB sandbox container (exit 137 / SIGKILL) on 5 consecutive attempts**:
1. full `yarn install --prefer-offline --check-files` → 137 (pod went Failed)
2. `--ignore-scripts` → 137
3. `--ignore-scripts --network-concurrency 1 --child-concurrency 1` → 137
4. `NODE_OPTIONS=--max-old-space-size=1536` → 137
Container cap confirmed: `memory.max = 2147483648` (2 GiB). The kernel OOM-killer terminated the pod before any message could flush, so I could NOT capture a literal "JavaScript heap out of memory" string.

## Root cause (inferred, with stated confidence)
The **frontend build stage is exhausting memory** during `yarn install` / `yarn build`. This app's frontend is unusually heavy: React 19 + the full `@tiptap/*` editor suite + `recharts` + `xlsx` + `react-snap` (puppeteer/Chromium), and the `reactSnap.include` list in `frontend/package.json` prerenders **80+ routes** with Chromium at build time. The `retry_with_backoff yarn install … && yarn build` wrapper returning "exit status 1" is consistent with the inner node/yarn being OOM-killed on each of its retries.

Confidence: The OOM behavior is reproduced repeatedly (strong), but note two caveats — (a) the sandbox cap (2 GiB) is smaller than a typical build host, so I could not prove the exact CodeBuild memory ceiling, and (b) I could not capture the verbatim CodeBuild error line. It is therefore possible the install actually completes in CodeBuild and the failure is in the equally heavy `yarn build` react-snap prerender step. Either way the failure locus is the frontend build stage and memory/resource pressure is the most probable driver.

## Why this surfaced now
The last 5 deploy runs were `secret_change`/`secret_reuse` that **reused the existing image** (sha256:6d3795…) with NO rebuild. This redeploy (force_repull) was the first real source rebuild in a while, so the frontend build is being exercised again and now fails.

## Suggested fixes (handoff to E1)
1. **Code (E1) — reduce frontend build memory footprint.** Reproduce the real build to capture the exact error, then: trim/disable the `react-snap` prerender (`reactSnap.include` currently prerenders 80+ routes via Chromium — the biggest build-time memory/CPU sink), and/or set `NODE_OPTIONS=--max-old-space-size=4096` for the `yarn build` step, and/or audit dependency bloat. This is the primary lever.
2. **Platform (escalate if needed).** If, after source optimization, the frontend `yarn install`/`yarn build` still exceeds the build container's memory ceiling, raise build-time memory for this deployment's CodeBuild/buildx stage.

I did NOT attempt a speculative manifest edit: the build-container memory cap is not cleanly manifest-controllable, and the exact failing command (install vs react-snap prerender) is not yet proven, so a blind manifest change risks a wasted attempt.
